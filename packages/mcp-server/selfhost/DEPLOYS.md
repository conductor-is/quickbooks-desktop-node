## 2026-10-26: OAuth 2.1 resource-server patch

- Render service: conductor-mcp is srv-da3mnkbbc2fs73acu8t0 (2 instances, auto-deploy on green CI from SDK main); the id in the 2026-08-18 entry is the retired original.
- Deploy: dep-dbfa4nmk1f9s73830o4g, commit da06775b1 (PR #250), live 2026-10-26T00:46Z, after the dashboard side (conductor PR #408) went live at 00:42Z.
- Shipped: credential-less `POST /` is 401 with `WWW-Authenticate: Bearer resource_metadata="https://mcp.conductor.is/.well-known/oauth-protected-resource"`; that document is served (resource `https://mcp.conductor.is/`, authorization_servers `https://dashboard.conductor.is`, no scopes); a non-Bearer scheme or an empty credential is 401 `invalid_request` instead of a 500 HTML stack trace; `Bearer`/`x-conductor-secret-key` keys pass through unchanged. The read-only connector URL ships in the same deploy: credential-less `POST /read-only` (and `/read-only/`) is 401 with `resource_metadata="https://mcp.conductor.is/.well-known/oauth-protected-resource/read-only"`; that document (served with and without a trailing slash) names resource `https://mcp.conductor.is/read-only` (no trailing slash: hosted Claude strips one and SDK clients compare lengths) and the same authorization server; the path rewrites the client permissions header to the client's own permissions minus every write before the generated code reads it (`{"allow_http_gets":true}` plus any client `blocked_methods`; a client `allowed_methods` sent without `allow_http_gets:true` becomes the exact GET methods it matches), so a client value never loosens it, and a malformed one gets the same 400 as on the root; `GET`/`DELETE /read-only` are 405; the key probe runs on the path as on the root. Deploy order: the read-only URL ships in the same deploy as the gate, so the OAuth order is unchanged (the conductor PR first, so the authorization server metadata is live, carrying the allowlist, consent copy, docs and MCP tab; then the `Authorization: Bearer sk_conductor_uptime_monitor` header on Betterstack 4826256; then this SDK deploy). Until both Render instances have rolled, the read-only docs and the MCP tab name a path that answers Express's 404, the same window in which the root sign-in answers no 401; the post-deploy checks are `curl -s https://mcp.conductor.is/.well-known/oauth-protected-resource/read-only | jq -r .resource` printing `https://mcp.conductor.is/read-only` and a credential-less `POST /read-only` answering 401, repeated until both instances do.
- Key probe: on `tools/call` only (never initialize, tools/list or notifications), `GET /v1/end-users/end_usr_oauth_probe` with the presented key, UA `conductor-mcp-key-probe/1`, 3 s timeout. A `valid` verdict is cached 60 s per key (a key deleted in the dashboard still passes this gate for up to a minute, though the API rejects it on every call), parallel calls with one uncached key share one probe, and a call to `search_docs` alone is never probed. Dead only when the API answers 401/403 `application/json` with the envelope code `API_KEY_INVALID` or `SECRET_KEY_REQUIRED`; everything else (text/html edge pages, other codes, 3xx, 429, 5xx, timeouts, network errors) fails open and the call proceeds in-band.

- Monitors: Betterstack 4826256 (`mcp.conductor.is`: POST initialize, keyword `conductor_node_api`, every minute) is the only MCP monitor. It sends `Authorization: Bearer sk_conductor_uptime_monitor`, a dummy the gate lets through because initialize is never probed; without it the check gets the 401. The /health monitor 4826254 was deleted, since a passing initialize implies it.
- Logs: `render logs -r srv-da3mnkbbc2fs73acu8t0 --text oauthGate` (values `missing`, `invalid_scheme`, `dead_key`); `render logs -r srv-da3mnkbbc2fs73acu8t0 --text keyProbe` (verdict, status, ms, contentType, cfRay, conductorRequestId; `unknown` is logged at warn and means the edge or the API, read status and contentType).
